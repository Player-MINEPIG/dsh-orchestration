# Native DSH integration

This implementation targets `@deepseek-ai/dsh@0.2.1-rc.2`, upstream commit `687f282e8625c6b8d11ff58211a90524be2e4317`, Cordis `4.0.5`, and Schemastery `3.18.5`. Acceptance runs use Node 26.5.1. The installed distribution is the official npm package. The DSH host, Loader, tool dispatcher, AgentLoop, session persistence, and lifecycle are real in the native tests; the external model and network peer are explicitly scripted.

## Host lifecycle

Install the built task-system tarball into a new custom profile. New custom profiles are base-backed. Do not initialize from `headless`: its runner exits after one task. These bundles mount inside the DSH host and ship no separately supervised plugin daemon.

```sh
npm run build
npm pack --workspace @dsh-task/task-system --pack-destination /path/to/artifacts
dsh plugin --profile tasks add /path/to/artifacts/dsh-task-task-system-0.1.0.tgz
dsh --profile tasks --patch /path/to/project/profiles/both.patch.yml --dump-config
dsh --profile tasks --patch /path/to/project/profiles/both.patch.yml
```

`profiles/planner.patch.yml`, `executor.patch.yml`, and `both.patch.yml` provide complete row configuration because DSH replaces a row's configuration rather than deep-merging it. Set `DSH_TASK_DATABASE` to a durable operator-controlled path and `DSH_TASK_NODE_ID` to the node identity. The task plugin's lifecycle-owned maintenance timer keeps the host active after boot. Supervisor start/restart/update remains external. SIGTERM drains the mounted host; DSH's own shutdown budget is finite, so accepted ledger state must survive forced termination too.

Operator configuration can bootstrap the route catalog without a custom startup plugin. `localNode` declares `models` (each with provider/model/reasoningEfforts), `capabilities`, `workspaceIds`, and `enabled`; the plugin supplies `nodeId` and derives its role from the host. Planner profiles cannot declare a local executor. `remoteNodes` accepts explicit remote node catalog entries for planner/both profiles. Executor profiles can register only their own node. Unchanged configuration does not generate another registration receipt on every boot. These declarations grant supported routes; they do not create credentials or provision directories.

The native entry is `@dsh-task/task-system/plugin`. It exports named `name`, `Config`, `inject`, and `apply`, without a competing default export. `Config` is native Schemastery. `ctx.taskSystem` owns the SQLite ledger and optional native execution provider. Only `tools` is a mandatory plugin dependency; native execution waits on `agents`, `agentLoop`, `sessions`, and `sessionPersistence`. Provider loss drains owned agents, and provider return creates a fresh execution provider.

## Outcome authority and recovery

The normal local sequence is:

1. Validate an explicit node/provider/model/effort/workspace route and atomically claim a run
2. Atomically bind a fresh invocation `executionId` with `markRunning`, then bind one session identity before creating or waking an agent
3. Create or explicitly resume an owned handle through `ctx.agents`
4. Execute under the configured tool set intersected with inherited task policy
5. Accept `task_submit_result` only from that exact owned agent; task/run/attempt/fence/execution ownership come from runtime, never model-supplied IDs
6. Conclude the turn, wait for quiescence, flush the native session, and dispose the owned handle
7. Fsync the exact result to the independent private native journal, then commit it through the fenced authority ledger

Final assistant text, an idle agent, and an inbox delivery receipt do not complete a task. Idle without an explicit structured result records `unknown`/`uncertain`. Tasks have no elapsed-time cutoff. Legacy `executionTimeoutMs` and `maxRuntimeMs` remain readable for migration but do not stop execution, resume, or safe retry. Cancellation requests preserve active resource ownership until the agent has stopped and the runtime records an acknowledgment. Lease loss, interruption, and unknown effects require reconciliation; there is no automatic replay of uncertain work.

The native result journal is `${databasePath}.results.sqlite`, separate from the authority database. It retains exact command, lease/owner/session binding, outcome, and post-quiescence evidence; it never reconstructs success from session text. Authority lock or commit-ack failure leaves a recoverable record. Boot and maintenance replay the same result without another model call. Recovery requires the same current attempt, fence, execution owner and session, no cancellation or reconciled terminal state, a ready timestamp within the persisted lease, and a 24-hour recovery window. Temporary validator absence remains held; invalid results remain preserved for review and cannot become success. The journal has finite entry/byte bounds and does not silently evict retained outcomes. If it fills, writing fails closed and requires operator maintenance. A crash after quiescence but before the journal commit is still an uncertain outcome.

`safeRetry` is disabled by default (`maxRetries: 0`). An operator can opt into at most two delayed continuations, with default delays of 30 and 60 seconds. The actual native event stream must prove a contiguous terminal transient request failure (`RATE_LIMIT`, `SERVER`, `TRANSPORT`, or `TIMEOUT`), zero tool calls and zero tool dispatches, persisted session state, quiescence, and disposal. Authentication errors, schema failures, missing results, cancellation, failed or unresolved tool results, and uncertain event coverage do not qualify. The same run, route, context and native session continue with a new attempt and fence; elapsed time does not limit continuation. The remote worker journals the witness and owns the authenticated retry transition.

A separate `safeRetry.resumableTools` list (default `[]`) enables continuation after explicitly reviewed tools have completed. Every call must have exactly one matching successful append-only result and one dispatch, with matching public event references; one invocation is bounded to 32 calls. The native host requires persisted results, a final transient provider error, quiescence and disposal. The core retains up to 160 deduplicated tool-name/validated-argument fingerprints across the bounded retries. A resumed tool guard rejects those exact invocations, and its wake message only asks to continue from persisted results, without resending the original task. Unknown or incomplete effects still require reconciliation.

This continuation boundary is for reviewed self-contained tools. A successful custom shell return does not prove the absence of detached background effects, and fingerprints prevent exact replay rather than every semantically equivalent operation. Operators must not treat the option as a general shell-effect or semantic-idempotency guarantee. Schema normalization that changes the raw arguments can conservatively disqualify a proof. The default zero-tool mode remains narrower.

A leased attempt with a persisted bound session that has not started execution can be resumed explicitly through `ctx.taskSystem.native.resume(claim)`. Every new invocation uses a fresh execution ID; an attempt already owned by another invocation refuses takeover before model or workload effects. A lost running invocation requires reconciliation before any new attempt. The bounded observer described below does not resume or dispatch tasks.

## Roles, scopes, and workload permissions

Planner profiles omit native execution and execution tools. A final tool guard also blocks non-planning calls; the ledger independently rejects local execution transitions from planner role. Executor profiles omit task-intent creation and cancellation tools and permit only schedule inspection. Ordinary service callers still cross ledger role, lease, node, workspace, and fencing checks.

Owned agents can query their own task and inspect descendant reports. Report writes derive task, run, and attempt identity from the owned agent. When explicitly granted in `executionTools`, `task_dispatch` atomically creates and dispatches a child through its authoritative ledger. The runtime fixes the parent lease and execution owner. The ledger enforces route policy, fanout, depth, and node capacity. Child policy can only narrow inherited grants. `task_create` remains a separate draft-only operation; owned agents use `task_dispatch` to create and execute a child together.

`task_wait` inspects descendant settlement without counting the waiting parent itself. Use `timeoutMs: 0` for an immediate query. Success or partial completion requires descendants to have settled through a quiet window. Concurrent local parent and child work needs sufficient capacity because a waiting parent still occupies its native execution slot.

`task_note` queues scoped context for a future run, retaining report and actor provenance. Queuing does not wake the current agent. The next run snapshots those notes as task data, which cannot grant tools, permissions, or configuration changes. Node catalog capacity defaults to the local native `maxConcurrent`, or one for configured remote nodes. A task's `settlementQuietMs` defaults to 1000; the core rechecks descendant settlement at final commit.

`executionTools` now defaults to following the DSH Agent preset (`null` or omitted), normally `standard`. The native adapter mounts that preset before deriving tools, records it in the session, and restores the recorded preset on resume. Normal shell, search, filesystem and other preset tools use the same DSH sandbox and approval rules as a WebUI session. Task `allowedTools` may narrow this catalog; lifecycle/result tools remain bound to the task owner and lease. The preset, rather than this plugin's legacy file guard, owns workload permissions in this mode.

An explicit `executionTools` array keeps the restricted mode. Known DSH file tools (`read`, `read_image`, `write`, `edit`) use `file_path` inside the canonical workspace, reject symlinks and broader `sandbox_permissions`, and protect the authority database, result journal, SQLite sidecars, plugin modules and `protectedPaths` (including hardlink aliases). Shell/custom tools in that mode require explicit `trustedUnconfinedTools: true`. These argument checks are not an OS sandbox and do not defeat hostile local processes racing filesystem changes. Task policy cannot grant a tool absent from the chosen preset or explicit list.

## Workspaces and automatic work

`workspaceRoots` defaults to `[]`. Configured entries have `id`, an existing physical `path`, and `allowCreate`. An unowned operator caller may use `task_workspace` with `action: provision` and a clean relative path to create or reuse a workspace through `WorkspaceManager`. The manager verifies roots, traversal, symlinks, ownership markers, and durable intent/retry identity. Planner and owned task-agent callers cannot provision. Raw metadata registration is not exposed as a model tool.

The maintenance timer admits due interval/cron occurrences using durable occurrence IDs and the stored explicit route. `autoExecute` defaults to false. Enabling it allows bounded native dispatch of queued runs routed to this node, up to `maxConcurrent` (default one). A schedule without a route remains queued until an authorized planning path assigns work. Automatic admission never implies success. Remote new-project provisioning is an explicit two-stage process under a configured device root; no network message can request arbitrary `mkdir` or supply a shell command.

`requireConfirmation: true` requires trusted approval for newly created tasks, even when a model requests `requiresConfirmation: false`. Runs can be queued while pending, but dispatch and claiming remain blocked. Approval uses the trusted `ledger.setTaskConfirmation` API with the task's current confirmation revision, actor and reason; there is no approval tool for models. Changed intent or a newly queued run invalidates a required prior approval, so approval covers the current queued plan. `task_create` can request confirmation and integer priorities `userImmediacy`, `importance`, and `urgency` from 0 to 100. The ledger applies its dispatch ordering after confirmation gates.

`reportDestinations` defaults to an empty list. Explicit operator configuration lets an accepted result enqueue a durable report or task-state item for those destinations. `configuration.reporting: "none"` suppresses this optional narrative; `summary` and `escalate` preserve the selected reporting flag. By default this narrative is for root tasks; child runs need an explicit terminal-notification setting. Models cannot select destinations through `task_submit_result`. `lifecycleDestinations` separately opts into task creation anchors and terminal replies. `alertDestinations` separately opts into health and operational alerts. Enqueueing is separate from channel delivery, which requires an independently enabled transport.

Planner/both profiles expose `task_curate` to unowned planning callers for reversible task admission. Dismissal hides a task from normal `task_query` results while preserving lifecycle, reports and history; `includeDismissed: true` includes those records. Curation requires the current admission revision and a reason, and the runtime records the caller identity. Owned execution cannot curate, and executor profiles omit this tool. New reports do not undo a dismissal.

## Live approval and host health

The optional `@dsh-task/task-system/approval-bridge` plugin uses DSH's public `approval/request` answerer. It is disabled by default. Enabling it requires an explicit `reviewableTools` list with each tool's permitted scalar `argumentKeys`. A request is offered only when the live owned tool call, actual validated arguments, task policy, session and execution owner can all be bound. Unreviewable, nested, oversized or recognizably sensitive arguments fall through to the normal host approval flow. The descriptor filter is bounded defensive screening, not a universal secret classifier; operators must review the tools and argument fields they expose.

The bridge holds that exact in-memory SDK callback while a trusted host or configured Feishu operator answers once or denies. `approvalDestinations` controls optional durable delivery independently of task-plan confirmation. No model tool or remote peer operation can respond. Before applying even an already-allowed decision, the bridge rechecks the live signal, exact call/session/task-attempt-owner binding and expiry. Delayed replies, unload and cancellation retire the held closure; persisted approval records cannot recreate it after restart. The bridge's request ID identifies its live closure because the SDK does not expose its internal audit ID in the public answerer event.

When `localNode` is configured, the native host records actual local runtime readiness and active execution count on readiness changes and at `localHeartbeatIntervalMs` (default 30 seconds). Provider status remains `not-probed`: readiness does not assert model-network health. `requireFreshHeartbeat` defaults to false, `heartbeatTtlMs` defaults to 60 seconds, and planner/both `healthAlerts` reconciliation is opt-in. `task_nodes` exposes allowed status reads; `task_alerts` is unowned planner-only. Models cannot acknowledge or resolve operational alerts.

## Optional typed planning and observation

Custom result templates can validate structured report fields under `report.data`. The native `task_submit_result` tool accepts `reportData` and `reportSchemaId`, and `task_report` accepts `data` and `schemaId`, alongside their human-readable text. A schedule snapshots its template's `resultContract` into the run; the ledger validates that contract before accepting the terminal result.

A trusted host plugin can additionally register a deterministic synchronous validator with `ledger.registerResultValidator(id, callback)` and dispose it with the returned function. `Template.resultValidator` selects that registered ID. Shape-valid output must also pass this semantic check; configuration cannot load validator code. A rejected native terminal result records unvalidated uncertainty, retaining resources for reconciliation instead of claiming success.

The planner/both profile exposes `task_plan` with or without the independent `decisionModels` service from `dsh-jev-plugin`. When enabled and available, planning submits caller-prepared context/questions to the shared model service. When disabled or absent, the caller preserves explicit routing or leaves the task pending routing. The task suite records its own audit; `task_plan` only proposes; `task_dispatch` applies the plan after authoritative catalog, expiry, and policy checks. A model answer does not grant execution or filesystem permission.

`observationEnabled` defaults to false. When enabled, a host-only native session projection captures bounded visible assistant text after direct human input. It excludes task-owned sessions, subagents, inherited prefixes, tool payloads, system/developer messages, and reasoning/stream content. Text is bounded and common credential-like patterns are masked before durable capture; this is not a general sensitive-data classifier. `observationMaxMessages` defaults to 64 and `observationMaxText` to 8000.

Capture creates pending candidates only. `task_observations` lets an authorized planner list, ignore, create an observed record, or attach a report. Observed work cannot be dispatched as a new execution. The projection supports live events, late plugin mounting, and resumed-session catch-up through supported `sessionProjections` APIs. When a resumed history exceeds the retained projection window, a catch-up-gap event records the omitted count. No complete retrospective coverage is claimed.

An additional explicit opt-in, `autoAdmitObservations: true`, lets the configured typed decision provider classify one pending candidate at a time. Its catalog contains no execution/model/workspace choices, the receipt is stored before applying admission, and application can only ignore, attach, or create an observed record. Existing receipts, including abstentions, prevent automatic paid retries on every timer tick. Abstentions remain available for manual review. Dependency loss aborts and drains decision work before the ledger closes. This option still cannot redispatch previously observed work.

A configured remote coordinator can subscribe with `ctx.taskSystem.subscribeObservations(sink)`. The native observer commits each local candidate before publishing it; subscription replays pending local candidates from the durable ledger. A failed transport leaves the local candidate available for restart replay. Only one authority sink may subscribe, and `autoAdmitObservations: true` rejects forwarding so two authorities cannot classify the same source automatically. Callback disposal uses a generation token across Cordis service proxies; shutdown aborts and drains sink jobs before closing the ledger. A sink must honor its `AbortSignal`. Delivery never creates a run or admits a task by itself.

The native projection retains the immutable session header's starting directory locally. The configured remote sink verifies that directory resolves within both the selected workspace and its allowed root before forwarding visible output. Candidates with missing or outside directories remain local for review; the directory itself is omitted from the wire payload. This bounds eligible session origins, but does not prove that all text in a session concerns that directory. Inbound remote source identities are excluded from local replay to prevent forwarding loops.

## Independent capabilities and remote integration

Typed decisions boots without a task-system or execution plugin. Its offline acceptance evaluates a configured deterministic rule. Feishu channel boots independently with networking disabled by default and supports consumer attach/detach without task-system. Enabling live Feishu transport requires real operator configuration and is not covered by offline delivery claims.

Remote execution depends on a host-provided `taskSystem` ledger seam, not on typed planning or Feishu. Its CLI acceptance uses the real ledger, SQLite recovery store, cryptographic protocol, and a synthetic signed external peer. A replayed nonce is rejected. A fresh signed nonce carrying the same command ID recovers its durable receipt. Forged signatures are rejected.

The remote worker uses `nativeExecutionAdapter` around `ctx.taskSystem.native.executeExternal(request)`. This execution-only method creates and drains the actual DSH agent and returns its structured outcome; the authenticated remote worker owns lease maintenance and settlement. It never borrows local task IDs or writes the executor host's unrelated local ledger. Scoped history, wait, report, note, and delegation use bound coordinator callbacks with a fixed lease and execution owner. Missing callbacks or peer grants fail closed. Native success/partial requires `taskWait` permission for the coordinator settlement check; delegation and the other scoped operations require their corresponding explicit grants. External global `task_create` remains withheld; `task_dispatch` uses the coordinator collaboration callback. The joined tests exercise two real native executor hosts, signed delegation, foreign-task denial, queued-note context, quiet settlement, and restart receipt recovery, with only model/network boundaries scripted.

The maintained optional task pack is distributed as `@dsh-task/task-system/task-pack/plugin`. An explicitly configured `legacy_report_prepare` tool prepares validated data without settling a running agent. Local root Agent Daily results create finalized artifacts under the operator's configured directory; native `task_submit_result.reportArtifactIds` accepts at most 32 unique IDs owned by that task, and the core verifies bytes at commit. External native execution accepts structured node/game/daily-work report data, but rejects artifact IDs without an authority-owned artifact-transfer path. Root artifact preparation therefore runs on its authority host. Before native journaling or remote return, `validateResultContract` runs with `phase: "executor-preflight"` against the authenticated claim. Source report kinds additionally require an exact prepared-envelope fingerprint from this live execution. A copied internally consistent old report cannot satisfy that gate. Authority settlement and durable journal replay use only deterministic semantic validation, so recovery does not depend on a lost in-memory receipt map. Configured `legacy_sources_read` captures only registered sources authorized by the frozen run input and returns attempt/execution-bound receipts; node/game/daily-work preparation consumes those receipts. Daily-work summaries derive included Codex/Hermes user-turn counts and theme shares from captured sources. Unloading the pack unregisters its validators and tools; pinned templates then fail closed. The optional `@dsh-task/task-system/task-pack/quota/plugin` is also disabled by default and does no credential reads, network work or timer creation while disabled.

## Reproducible validation

From the repository root:

```sh
npm run build
node --test tests/dsh/native-loader.test.mjs tests/dsh/remote-native.test.mjs
node tests/dsh/demo-local.mjs
node tests/dsh/distribution-acceptance.mjs
node tests/dsh/capability-distribution.mjs
node tests/dsh/finalize-packages.mjs
```

Both distribution runners install the exact official DSH version into isolated temporary directories when no `DSH_TEST_RUNTIME_DIR` is supplied. They use isolated `DSH_HOME`, user-assets paths, caches, profile manifests, and databases. `DSH_TEST_RUNTIME_DIR` can reuse a verified pinned install; `DSH_TEST_STORE_DIR` selects a package-store preference. Installation allows only explicitly named official dependency build scripts. No production profile, real credential, live model provider, or live Feishu account is used.

The task distribution runner packs built code, invokes actual `dsh plugin add`, dumps configuration and native schemas, boots all three persistent role profiles, sends SIGTERM, invokes actual `dsh plugin remove`, and boots again without the removed service while checking retained state. The capability runner repeats real install/boot/remove for the standalone decision package, the task suite with its remote export, and the optional Feishu adapter. Machine-readable receipts live under `tests/dsh/results/` and identify exactly what passed; these are runtime evidence, unlike configuration dumps alone.

The installed task-system probe mounts the packaged task-pack entry, performs native root report preparation and settlement, and mounts disabled quota and approval bridge modules. The installed typed-decision probe also mounts the ordinary-model completion bridge and calls the native LLM service with a scripted external model. The installed Feishu probe mounts its optional native-chat module disabled. The remote probe verifies signed result and observation intake, structured report fields, and a registered semantic validator. Receipts include npm tarball integrity values. `finalize-packages.mjs` repacks both core distributions and the optional channel adapter, checks every byte against both successful CLI receipts, and retains the tarballs under `tests/dsh/results/final-packages/` with SHA-512 integrity and SHA-256 hashes. A package changed after validation fails this comparison.

Offline tests do not establish model quality, live Feishu delivery, public TLS deployment, cross-device operating-system behavior, Windows supervisor behavior, or production suitability. Publishing packages or deploying a host remains separate from this isolated implementation and validation.

Official Codex execution uses `ctx.subagents.startActivation` with `delivery: "caller"`. The activation returns `childId`, `result`, and `dispose`; task-system awaits disposal before returning evidence or propagating cancellation. The parent must be the exact live Agent registered with DSH. The official provider owns native execution permissions, and task-system does not pass unsupported agent options, presets, output schemas, or depth overrides.

DSH 0.2.1-rc.2 pins Zod 4.4.3 for its session projection and subagent APIs. Task-system uses the same version for projection schemas. Its custom host-only observation fold has an explicit `ZodType<ObservationFold>` schema.
