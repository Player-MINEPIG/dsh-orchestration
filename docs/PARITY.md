# Source-grounded outcome parity

This is an implementation correspondence, not a statement that every production gate has passed. It replaces the earlier high-level claim that configurable templates alone preserve all legacy report and collector outcomes. The maintained task pack supplies actual readers, deterministic builders, semantic validators, artifact preparation and renderers; its configuration selects capabilities rather than silently dropping them.

Reviewed source pins: Hermes Plugins `1dfacb5e5949d9f248b1feacbc36644fb351f19e`, Shared Assets `774e49583eca39ba8979d4a252913bef45a22bc8`, DSH `639ed015397290b3745d163aafe02ffee4aa3f84` / npm `0.2.0-rc.2`. The verified local handoff supplements source/history; it does not establish an unseen replacement runtime. Original code is read-only and not copied into the MIT distribution.

## Reading the status

- **ImplementedEquivalent**: executable replacement exists with the stated offline acceptance. Mechanisms can differ; any material behavior correction is identified below
- **ImplementationPending**: a concrete old observable behavior lacks a completed equivalent. A generic API, example idea or in-progress edit is not completion
- **LiveAcceptancePending**: implementation/offline acceptance exists, but this row concerns a real installation, account, peer or delivery gate that has not been exercised
- **ExplicitlySuperseded**: the user explicitly chose a different mechanism or scope. This label is not used merely because a source behavior is inconvenient

`U` below means deterministic tests with synthetic input; `N` means actual pinned DSH Loader/AgentLoop/session services with scripted external model/transport; `W` means real SQLite/cryptographic/loopback wire components with scripted peer/provider boundaries; `CLI` means actual official DSH installation/boot/removal. None of these means a live model/account/network result. Test filenames identify acceptance bodies, not an assertion that a test was run during the old research phase.

Implementation links use `packages/*/src` and `examples/legacy-task-pack` (the latter is distributed under `@dsh-task/task-system/task-pack`, `/task-pack/plugin`, `/task-pack/quota` and `/task-pack/compatibility`). Historical DT/EX/FR/DM IDs refer to the 228-row research dossier; those rows and 751 source-function associations are traceability, not implementation or test totals.

## Authorized deployment extensions (0.1.1)

The user subsequently requested an operator-configured whitelist limited to the current network address snapshot. The optional `trusted-network` mode therefore supplies exact IPv4/IPv6 address admission separately from node/role/operation/workspace/capability grants, without automatic discovery, signing keys, SSH, DNS or authentication fallback. Production addresses are kept in private acceptance profiles, not product defaults. The mode relies on its explicitly trusted network and does not claim a separate process identity or automatic Tailscale WhoIs verification. Default signed + TLS behavior remains available.

A live-test preparation probe also exposed loss of native error detail: an owned DSH `MISSING_CREDENTIAL`/`NO_ADAPTER` previously became a generic unknown summary. The 0.1.1 fix forwards only a fixed safe terminal code; unknown codes map to `RUNTIME_ERROR`. Outcome remains unknown, no report is invented, and credential errors do not gain retry authority. Actual signed and trusted-network DSH fixtures cover this behavior with the official empty-key adapter and no live API calls. These additions do not retroactively turn any production gate into a pass.
